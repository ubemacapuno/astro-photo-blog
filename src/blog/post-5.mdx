### Why I built this

As part of my stretch goal to learn more about Laravel, I decided to build a small demo following [Laravel's eventing](https://laravel.com/docs/13.x/events#generating-events-and-listeners) system. I built a tiny ERP-inspired app (`miniERP`) around placing an order. When an order is placed, a bunch of things need to happen:

1. stock gets deducted
2. an invoice gets generated
3. and (eventually) emails and reorder alerts go out (I didn't implement this, but this can be easily added with these eventing/listener patterns)

<br />

One way to do this is to place all these things into the controller. For this small app that is probably fine, but if we're thinking scalability, it makes sense to contain the eventing logic in separate files. Otherwise, every new side-effect means editing the same method. I used this as an excuse to learn **Events**, **Listeners**, and **Jobs/Queues**. You can find the demo [here on GitHub](https://github.com/ubemacapuno/miniERP).

<br />

### The mental model

These were the three main features I wanted to explore and demo:

<br />

- **Events**: An announcement when an order is placed. The event I made carries order data, but alone does nothing itself.
- **Listeners**: These listen for the announcement when the order is placed and react. Multiple listeners can react to the same event, independently.
- **Jobs**: These are like "To-dos" that are queued up to be done _later_, by some worker. In this demo, the worker can be started up with `php artisan queue:work`

<br />

So my whole flow in the demo is just one announcement (Events), some reactions (from Listeners), and a couple of to-dos (Jobs).

<br />

Folder structure:

<br />

```
app/
├── Http/
│   └── Controllers/
│       └── OrderController.php          // dispatches the event when an order is placed
├── Events/
│   └── OrderPlaced.php                  // the announcement
├── Listeners/
│   ├── DeductStock.php                  // decrement stock
│   └── DispatchInvoiceGeneration.php    // kick off the invoice job
└── Jobs/
    └── GenerateInvoiceJob.php           // create the invoice (queued)
```

<br />

Laravel gives you artisan commands to scaffold each of these (`make:event`, `make:listener`, `make:job`), so they land in the right folder automatically.

<br />

### The event

`OrderPlaced` announces the order and nothing else:

<br />

```php
class OrderPlaced
{
    use Dispatchable, SerializesModels;

    public function __construct(public Order $order) {}
}
```

<br />

This looks surprisingly simple (don't we need some logic in here??), but events don't need logic. They just need to announce "this happened, here's the data", and that's enough for a listener to act on. Note that the `SerializesModels` trait matters once you queue things, because it stores the model's ID and re-fetches a fresh copy later instead of trying to serialize the whole object.

<br />

### Dispatching

In the controller, after I create the order inside a database transaction, I dispatch the event:

<br />

```php
$order = DB::transaction(function () use ($validated): Order {
    // ...create the order + line items, snapshot prices, compute total
    return $order;
});

// We could call each reaction inline here...
// (new DeductStock)->handle(new OrderPlaced($order));
// GenerateInvoiceJob::dispatch($order);

// ...but for the purpose of the demo, use an event instead:
OrderPlaced::dispatch($order);

return redirect()->route('orders.show', $order);
```

<br />

The dispatch is **after** the database transaction. If you fire the event inside the transaction and something rolls back, your listeners will have acted on data that no longer exists. Dispatching after the commit keeps things consistent.

<br />

### The two listeners

`OrderPlaced` has two listeners, `DeductStock` and `DispatchInvoiceGeneration`:

The first, `DeductStock`, does the decrementing within the listener:

<br />

```php
class DeductStock
{
    public function handle(OrderPlaced $event): void
    {
        foreach ($event->order->items as $item) {
            $product = $item->product;

            // do the decrementing here within the listener
            $product->decrement('stock_quantity', $item->quantity);

            Log::info('Stock deducted', [
                'sku' => $product->sku,
                'quantity' => $item->quantity,
                'remaining' => $product->stock_quantity,
            ]);
        }
    }
}
```

<br />

The second, `DispatchInvoiceGeneration`, doesn't do anything itself, it just forwards to a queued job:

<br />

```php
class DispatchInvoiceGeneration
{
    public function handle(OrderPlaced $event): void
    {
        GenerateInvoiceJob::dispatch($event->order);
    }
}
```

<br />

In Laravel 11+, listeners in `app/Listeners` are auto-discovered by the type-hint on their `handle()` method, e.g. `handle(OrderPlaced $event)`.

<br />

### The job, and sync vs. queue

The actual invoice gets created by a queued job:

<br />

```php
class GenerateInvoiceJob implements ShouldQueue
{
    use Queueable;

    public function __construct(public Order $order) {}

    public function handle(): void
    {
        $invoice = $this->order->invoice()->create([
            'invoice_number' => 'INV-' . str_pad((string) $this->order->id, 6, '0', STR_PAD_LEFT),
            'amount' => $this->order->total,
            'status' => 'issued',
            'issued_at' => now(),
        ]);

        Log::info('Invoice generated', [/* ... */]);
    }
}
```

<br />

The `implements ShouldQueue` is what decides when this job runs, and that's controlled by your `QUEUE_CONNECTION` in `.env`:

<br />

- `QUEUE_CONNECTION=sync` -> jobs run immediately inline in the same request. No worker needed. Great for local dev.
- `QUEUE_CONNECTION=database` -> jobs are saved to the databse (`jobs` table) and run later by a worker you start with `php artisan queue:work`.
